# Dageno Topic 与 Prompt 生成器

[English](README.md) · [Dageno](https://dageno.ai/) · [使用规范](SKILL.md)

**从真实网站与行业研究出发，建立有依据、可复核的 AI 搜索监控问题体系。**

当前为 V3 候选版：程序校验已通过，完整真实模型回归尚未完成，不宣称已经验证生产识别准确率。

不是给一个域名套上行业模板，而是先弄清楚：这家公司今天卖什么、谁会付钱、客户怎么选、同行还覆盖了哪些需求。

## 为什么要先设计问题，再监控可见度？

只监控品牌擅长的问题，可见度可能偏高；把不相关行业也算进去，又可能偏低。
问题集合决定了监控结果代表什么。

V3 把品牌核心能力、同品类需求、竞争机会和范围外参考分开，避免把不同口径混成一个漂亮但不好解释的分数。

## 一套完整流程

```text
读取网站与外部搜索
  → 提出业务假设
  → 用市场和竞品证据复核
  → 确定 L3 品类边界
  → 梳理买家决策与细分意图
  → 独立查漏
  → 聚类成 Topic
  → 每个独立意图写一个自然问题
  → 检查语义、证据与覆盖
  → 输出导入 CSV 和完整 JSON
```

例如，“适合小团队的工具推荐”换一种说法，通常还是同一个意图；“企业安全审查”“迁移成本”“价格限制”则可能是不同决策，不能因为都属于购买前问题就合并掉。

## V3 的改进

| 改进 | 解决什么问题 |
| --- | --- |
| 两轮业务判断 | 第一轮判断错误时，有后续证据纠正，而不是一路写下去 |
| 先意图、后 Topic | 不再先定 7 个主题，再硬凑每组 10 条问题 |
| 独立行业研究 | 保留品牌不擅长但市场真实存在的需求 |
| 真正读取竞品页面 | 区分搜索摘要、第三方观点与厂商自己的能力说明 |
| 意图粒度去重 | 不把同义改写当作新增覆盖；相似但不同的决策不自动删除 |
| 双层 QA | 程序查字段和映射，独立模型查业务与语义 |
| 中文与地区设置 | 简体、繁体、监控国家、实际本地需求分别处理 |
| 版本差异 | 看清保留、新增、移除、措辞变动，避免历史口径悄悄变化 |
| 同源发布 | Skill、运行模块和发布清单可通过文件哈希核对 |

## 交付什么？

- 一份通俗的业务判断和 Topic 设计理由；
- 按 Topic 分组的监控问题和内容机会；
- 正式导入 CSV：只有 `topic,prompt,regions,language` 四列；
- 完整 JSON：包含来源、意图 ID、品类、用途、复核和版本信息。

默认不含品牌词，不固定 Topic/Prompt 数量。需要控制成本时，可设置人工数量上限，但会列出暂未覆盖的已知意图，不会称为全部覆盖。

## 如何使用？

按 [英文安装步骤](README.md#quick-start-in-codex) 安装后，在 Codex 中直接说：

> 把 example.com 当作第一次看到，研究真实业务及所在行业。生成美国地区、英文、不含品牌词的 Topic/Prompt 方案。给我中文设计说明、完整 JSON 和可直接导入 Dageno 的四列 CSV。

Codex 会话可以使用当前模型与研究工具，不需要为了调用 Skill 再提供一把 OpenRouter Key。
只有线上系统或独立 CLI 需要配置服务端 OpenRouter Key 和模型 ID。

## 数据边界必须讲清楚

**穷举目标是尽量覆盖有依据的行业决策，不是宣称拿到了全部真实用户查询。**

生成的问题属于研究设计，不是用户搜索日志。模型分数不是搜索量、真实需求频率或品牌提及概率。
官网说自己支持某项能力，不等于已独立验证其效果。没有找到某项能力，也不代表它一定不存在。
不同语言、不同地区和不同品类，需要保留可比较的口径。

默认流程没有执行真实 AI 平台监控，也没有实体提及抽测；相关数据会明确标记未运行。
自动测试中的多行业样例验证的是流程和隔离，不会被包装成联网识别准确率。
